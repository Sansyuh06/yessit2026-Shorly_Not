### Design (B) — minimal shape

```text
qds-shield/                 # NEW root for SIH 26141
  qds/
    bell_pke.py             # Bell pairs = quantum public key material
    teleport_sign.py        # sign message bits via teleportation + Pauli
    verify.py               # Pauli correction + projective measure → accept/reject
  detect/
    thresholds.py           # mismatch rate, replay nonce, identity check
    threats.py              # FORGERY | REPLAY | IMPERSONATION | CHANNEL | OK
  attacks/
    simulate.py             # run the 4 attacks, return metrics
  analysis/

  app/
    cli.py                  # sign | verify | attack-suite

  tests/

  docs/
    DELIVERY_TABLE.md
    MODEL.md                # short math: protocol + thresholds
  README.md
```

**Protocol (honest, sim-grade):**
1. Distribute Bell pairs (signer keeps half, verifier half)  
2. Message → bits → encode on Pauli eigenstates  
3. Teleport / correct with classical Pauli bits  
4. Verifier measures; compare to expected  
5. Accept iff mismatch ≤ τ (and nonce fresh, key id matches)

**Detection (no ML):**
- mismatch > τ → forgery / channel  
- reused signature id/nonce → replay  
- wrong entangled share / key id → impersonation  
- elevated random errors with intact classical header → channel manip  

**Demo flow (judges):**  
Legit sign → green · Forge → red + P_forge · Replay → red · Impersonate → red · Chart of P_forge vs length  

**UI (Taste/Impeccable later):** dark ops dashboard, one column, big status, no generic AI purple goo. Core first.

## 6. Core protocol (Phase 1 — what we implement)

**Roles:** Alice (signer), Bob (verifier), Trent (arbiter) — matches Q13.

**Flow (simplified controlled-teleportation QDS, sim-faithful):**

1. **Setup:** entangled resource distributed (Bell/GHZ-style as profile dictates); key material IDs bound to parties.  
2. **Sign:** message → bit/block encoding into Pauli eigenstates; Alice does Bell measurement / teleportation steps; produces signature transcript (quantum outcomes + classical Pauli bits + nonce + key_id + profile).  
3. **Classical path:** correction bits optionally wrapped with **PQC** (QRQT-inspired).  
4. **Verify:** Bob (+ Trent if arbiter mode) applies Pauli corrections, projective measurements, compares to expected; compute mismatch stats.  
5. **Detect (Q-STDF):** threshold rules → `OK | FORGERY | REPLAY | IMPERSONATION | UNAUTH_VERIFY | CHANNEL`.  
6. **Analyze:** log metrics for the evaluation suite.

**Legit path:** accept with high probability under declared noise; ideal channel → deterministic accept.  
**Forge path:** random/Pauli-tampered sig → reject + high detect rate.  
We document known paper attacks (Gao/Lu cryptanalysis) and show **detector catches the sim versions**.

## 7. Detection design (your “all features” + τ)

**τ (threshold):**  
Not magic. For mismatch count \(X\) over \(n\) checked qubits, under honest noise \(p_0\):

\[
\tau = p_0 + \epsilon,\quad \epsilon \sim \sqrt{\frac{\ln(1/\delta)}{2n}}
\]

(Hoeffding-style; show formula in UI).  
Presets: **strict / normal / lenient** (your Q20 = show both error types).

**Feature pack (Q17 all + extras):**

| Feature | Threat |
|---|---|
| Mismatch rate > τ | forgery / channel |
| Pauli histogram divergence | forgery / wrong encoding |
| Nonce / sig_id reuse | replay |
| key_id / share binding fail | impersonation |
| Verify without entitlement | unauthorized verification |
| Correction MAC/PQC fail or bit flips | channel manip |
| **Novelty:** cross-backend disagree (Qiskit vs PennyLane) | implementation/channel anomaly |
| **Novelty:** adaptive τ shift when real-API noise rises | device-aware detection |

**No sklearn, no torch.** Ever.

# How the whole thing works (when it’s done)

Plain version. End to end.

---

## The cast

- **Alice** — wants to sign something (“pay Bob ₹10,000”)
- **Bob** — wants to check it’s really from Alice and wasn’t faked
- **Trent** (optional) — referee if Alice and Bob don’t fully trust each other
- **Attacker** — tries forge / replay / pretend to be Alice / mess with the channel
- **ShorlyNot** — the system in the middle that does sign, verify, and threat checks

---

## Big picture in one breath

```text
Alice signs a message the quantum way
        ↓
a signature package is created
        ↓
Bob (and maybe Trent) verifies it
        ↓
ShorlyNot looks at the measurement numbers
        ↓
ACCEPT  or  REJECT + threat type
```

No ML. Just quantum steps + simple math thresholds.

---

## Step 0 — Setup (once, before signing)

1. System creates **entangled pairs** (Bell-type links).  
   Think: Alice and Bob each hold matching “quantum halves” that are correlated.

2. Those halves act like **quantum key material** for signatures  
   (not the same job as a normal password, but same idea: only the right parties have the right stuff).

3. Everyone gets IDs: `key_id`, who is Alice, who is Bob, etc.

4. Optional: classical messages (correction bits later) can be wrapped with **PQC** so a normal hacker can’t easily read/flip them.

After setup, the system is idle and green.

---

## Step 1 — Alice signs

Alice types a message (or a payment form).

What ShorlyNot does:

1. Turn message into **bits**
2. Encode bits into **quantum states** (Pauli eigenstates — basically “this bit is prepared this way on the Bloch axes”)
3. Use **teleportation-style** steps with the entangled pairs:
   - Alice does a Bell-type measurement
   - That produces **classical correction bits** (the Pauli correction info)
4. Bundle a **signature object**:

```text
signature = {
  message (or hash),
  measurement / quantum transcript,
  Pauli correction bits,
  nonce (one-time id),
  key_id,
  profile (e.g. teleport / arbiter),
  timestamp
}
```

5. That signature is what gets sent to Bob (over normal network as data the app understands; the “quantum” part was simulated/prepared in the engine).

**Important:** each honest sign should burn one-time material (nonce + key chunk) so the same signature can’t be freely reused forever.

---

## Step 2 — Bob verifies

Bob receives: message + signature.

What ShorlyNot does:

1. Check basic stuff first (fast, classical):
   - is `nonce` new? (not seen before)
   - does `key_id` match Alice?
   - is Bob allowed to verify this?
   - is signature format sane?

2. If those fail → **stop early**  
   - reused nonce → **REPLAY**  
   - wrong key / wrong person → **IMPERSONATION**  
   - not allowed → **UNAUTH_VERIFY**

3. If basics pass → **quantum verify path**:
   - apply **Pauli corrections** using the classical bits
   - do **projective measurements**
   - compare outcomes to what the message/encoding says should happen

4. Compute **mismatch rate**  
   (“out of N checks, how many disagreed?”)

5. Compare to threshold **τ**:
   - mismatch ≤ τ → **ACCEPT** (looks legitimate)
   - mismatch > τ → **REJECT** (looks forged or channel-broken)

τ is not vibes. It’s set from expected noise + a safety margin so honest noise doesn’t always trip the alarm, but random fakes usually do.

---

## Step 3 — Threat detection (always on top of verify)

Every verify produces numbers. The detector reads them and stamps a label.

| What it sees | Label |
|---|---|
| Clean, low mismatch, fresh nonce, right key | `OK` |
| Random/fake signature, high mismatch | `FORGERY` |
| Old signature sent again | `REPLAY` |
| Right-looking format, wrong quantum identity | `IMPERSONATION` |
| Someone verifying without permission | `UNAUTH_VERIFY` |
| Correction bits flipped / noise spike / weird histograms | `CHANNEL` |

Rules only. Like:

- if nonce in used-set → REPLAY  
- if key_id unbound → IMPERSONATION  
- if mismatch > τ → FORGERY or CHANNEL (depending on other signals)  
- if Pauli histogram looks nothing like honest encoding → FORGERY  

That’s the “cyber threat detection framework” the PS wants.

---

## Step 4 — What the user sees when it’s working

### Normal day
1. Alice hits **Sign**  
2. Bob hits **Verify**  
3. Screen goes **green ACCEPT**  
4. Mismatch is small (e.g. 1–3% from noise)  
5. Log line: `OK · 2.1 ms · mismatch 0.02 · τ 0.08`

### Attack day
Someone hits **Forge** (or a real attacker sends junk):

1. Verify runs  
2. Mismatch jumps (e.g. ~25–50%)  
3. Screen **red REJECT**  
4. Label **FORGERY**  
5. Metrics update: forge attempts detected, \(P_{\text{forge}}\) display  

Replay:
1. Same signature sent twice  
2. Second time dies on nonce check  
3. **REPLAY** even if quantum part would have looked fine  

So working system = **two layers**:
- quantum verify (does physics match?)  
- threat rules (is this a known dirty pattern?)

---

## Step 5 — Evaluation lab (also always there)

In the background / metrics tab the system can run many trials:

- 1000 honest signs → almost all accept  
- 1000 forgeries → almost all reject  
- estimate **forgery probability** (chance a faker slips through)  
- show false reject (honest rejected by mistake)  
- show latency  

That’s how you “evaluate the framework” like the PS says.

---

## Optional layers (platform, not the main loop)

These can sit around the same flow:

**QKD module**  
Sometimes used to make shared session keys for encrypting traffic or protecting classical channels — side feature.

**PQC module**  
Wraps the classical Pauli correction bits so flipping them mid-wire is harder.

**Edge/modem (later)**  
Control PC does heavy quantum sim.  
A light box only checks the **signature transcript** + thresholds + “block/alert”.  
Same logic, weaker machine.

Ignore hardware for now: on a laptop, control plane does everything.

---

## Full lifecycle of one message

```text
1. SETUP
   entangled key material ready
   Alice, Bob registered

2. SIGN (Alice)
   message → quantum encode → teleport-style sign
   → signature package + nonce

3. SEND
   message + signature to Bob
   (correction bits optionally PQC-protected)

4. VERIFY (Bob)
   classical checks (nonce, identity, permission)
   → quantum corrections + measurements
   → mismatch vs τ

5. DETECT
   rules stamp OK or threat type

6. RESULT
   ACCEPT or REJECT
   log + metrics updated

7. CONSUME
   nonce / one-time key chunk marked used
   (replay next time will fail)
```

That’s the whole engine, looping every time someone signs.

---

## Mental model (simplest)

Think of a **wax seal**, but quantum:

1. Alice melts the seal in a special way only her entangled material allows  
2. Bob checks if the seal pattern matches the letter  
3. ShorlyNot also checks:  
   - is this seal photocopied from yesterday? (replay)  
   - is it a random blob? (forgery)  
   - is it someone else’s seal? (impersonation)  
   - did someone smudge it in transit? (channel)  

Working product = that loop, live, with numbers, every click.

---

## What “working” means in practice

You can sit down and:

1. Sign a real-looking message → always (or almost always) accepted  
2. Press forge → rejected and labeled  
3. Press replay → rejected  
4. Press impersonate → rejected  
5. See a graph that forgeries get harder as you use more quantum material  
6. See verify finish in milliseconds for normal sizes  

If those six things happen, **the project is working** — as a whole system, not as scattered quantum demos.

That’s the general working picture: **setup → sign → verify → threshold detect → accept/reject + logs/metrics**, repeat.

# Quantum-wise: how the whole thing runs

Think in **3 acts**.

## Act 0 — Setup (once / per session)

1. System prepares **Bell pairs**:

\[
|\Phi^+\rangle = \frac{|00\rangle+|11\rangle}{\sqrt{2}}
\]

2. One half is treated as signer-side resource, one as verifier-side resource  
   (in software: simulated shared entanglement).

3. Parties get IDs / `key_id` binding (who is Alice).

4. Optional: QKD-style session material for support keys; PQC ready to wrap classical bits.

---

## Act 1 — Sign (Alice sends money)

Transaction becomes a bitstring (hash of: from, to, amount, id, time).

For each bit / check position:

### 1) Encode into Pauli eigenstates (BB84-style states)

| bit | basis | state |
|-----|-------|--------|
| 0 | Z | \|0⟩ |
| 1 | Z | \|1⟩ |
| 0 | X | \|+⟩ |
| 1 | X | \|−⟩ |

So the message is not “just classical bits floating” — it’s prepared as **quantum states**.

### 2) Teleportation-style signing

- Message qubit + Alice’s half of Bell pair  
- Alice does a **Bell measurement**  
- She gets two classical bits \((m_1, m_2)\)

Those are the **Pauli correction bits**.

### 3) Signature object (what we store/send)

```text
Signature =
  payload hash
  + key_id
  + nonce (anti-replay)
  + bases
  + correction bits (m1,m2)
  + measurement transcript
  + backend/engine tags
```

Optional: **PQC/AES wrap** the correction bits so flipping them mid-wire is harder.

**Bank UI:** Alice only clicked “Transfer.”  
**Quantum layer:** seal was made.

---

## Act 2 — Verify (is this seal real?)

Bob / bank engine:

### 1) Classical binding first
- nonce new?  
- key_id really Alice?  
- allowed to verify?  

If not → **REPLAY / IMPERSONATION / UNAUTH** (often before deep quantum stats).

### 2) Quantum verify
For each check:

1. Unwrap corrections if protected  
2. Apply Pauli correction:

| (m1,m2) | correction |
|---------|------------|
| 00 | I |
| 01 | X |
| 10 | Z |
| 11 | XZ |

3. If basis was X → apply H  
4. **Projective measure** in Z  
5. Compare to expected bit  

### 3) Mismatch rate

\[
\hat{p} = \frac{\text{number of wrong checks}}{n}
\]

### 4) Threshold τ (Hoeffding, not random)

\[
\tau = p_0 + \sqrt{\frac{\ln(1/\delta)}{2n}}
\]

Defaults we locked: \(p_0=0.02\), \(n=64\), \(\delta=0.01\) → **τ ≈ 0.21**

- \(\hat{p} \le \tau\) and binding OK → **ACCEPT / OK**  
- else → **FORGERY** or **CHANNEL** (depending on signals)

That’s the quantum heart of “is this signature legit?”

---

## Act 3 — Threat detection + bank lock (Q-STDF)

Q-STDF is **not** a separate quantum algorithm.  
It’s the **decision framework** on top of quantum verify + classical checks:

| Signal | Label |
|--------|--------|
| high mismatch | FORGERY |
| reused nonce | REPLAY |
| wrong key binding | IMPERSONATION |
| no permission | UNAUTH_VERIFY |
| corrupted corrections / channel flags | CHANNEL |

Stages S0→S4 → **bank app locks** (no iptables needed for main demo).
